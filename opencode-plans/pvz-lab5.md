# Plan contract: pvz-lab5

> Disk source of truth. Re-read before each decision and after any compaction.

**Goal:** Реализовать лабораторную работу №5 «Пункт выдачи заказов» (https://antonagalakov.github.io/courses/MRT/lab5) в виде Java-веб-приложения в модуле `pvz/`: Spring Web (Spring Boot 4.1.1, Java 25) + Thymeleaf UI + JDBI для доступа к PostgreSQL + Flyway-миграция схемы `orders`. Функциональность 1:1 повторяет C++-референс из `si/`: приёмка заказа (по телефону или артикулу, с ячейкой и авто-генерацией кода `PVZ-000042`), поиск/фильтрация списка, выдача и отмена (только из статуса `ready`), отчёт по трём вкладкам со сводкой, очистка истории (удаление `issued`/`cancelled`). Проект собирается через `pvz/gradlew.bat`, все тесты зелёные, чек-лист приёмки лабы (раздел «Чек-лист», 18 пунктов, адаптирован в конце контракта) проходит.

## Архитектурное решение (design)

- Пакеты: `io.allitov.pvz` — `model` (Order, Report — сущности/модели, интерфейсы не нужны), `db` (Database, DatabaseImpl, JdbiConfig), `web` (OrderController), `util` при необходимости.
- `Order` — поля как в `si/db.h` (Lombok `@Data` + `@Builder`), `status` — String (ключ БД), `createdAt` — String `YYYY-MM-DD HH:MM` (форматируется при маппинге строки из БД). `Report` — три int-поля (Lombok `@Data` + `@Builder` или `@Value`).
- Статусные подписи/цвета — enum `OrderStatus` (READY/ISSUED/CANCELLED) с `ru`-подписью и CSS-классом + статические хелперы `fromDb(String)`, либо маленький Spring-bean; шаблон использует класс `status-ready|status-issued|status-cancelled`. Точный способ — на усмотрение coder, требование: русские подписи и цвета в одном месте, без дублирования в шаблонах.
- `DatabaseImpl` — Spring `@Repository`-компонент (без spring-data; аннотация `org.springframework.stereotype.Repository`), оборачивает JDBI `Handle`; каждый метод — SQL-запрос(ы) через JDBI, без промежуточных контейнеров. RowMapper для `Order` — свой (COALESCE/`rs.getString` с заменой NULL на «»). `addOrder` — `jdbi.inTransaction` / `handle.useTransaction`: INSERT … RETURNING id → `PVZ-%06d` → UPDATE.
- `JdbiConfig` — `@Configuration` с `@Bean Jdbi jdbi(DataSource ds)` (`Jdbi.create(ds)`), регистрация RowMapper'а.
- Веб (PRG-паттерн): `OrderController` — `GET /` (список: `listOrders(filter)` + клиентский/контроллерный статус-фильтр «Все|К выдаче|Выдан|Отменён»), `GET /orders/new` (форма приёмки), `POST /orders` (валидация как в dialogs.cpp; успех → flash «Принят заказ CODE» → redirect `/`), `POST /orders/{code}/issue`, `POST /orders/{code}/cancel` (отказы БД-метода → flash-сообщение об ошибке в статус-бар, redirect `/`), `GET /report` (три списка `listByStatus` + сводка из `buildReport()`), `POST /orders/cleanup` (0 → flash «Нет выданных или отменённых заказов.», иначе confirm-count и flash «Удалено заказов: N»). Выбор строки в таблице — radio по `code` в общей форме + кнопки-сабмиты (web-эквивалент выбора строки FLTK); подтверждения — inline `onsubmit="return confirm('…')"`. Статус-бар — flash-атрибут (`msg` + CSS-класс цвета) либо «Готово • Заказов: N».
- Шаблоны: `templates/orders.html`, `templates/order-add.html`, `templates/report.html` + `static/css/style.css` (палитра из `si/theme.h`). Thymeleaf-фрагменты для строки таблицы (переиспользуется в отчёте).
- Валидация приёмки — в контроллере (зеркало dialogs.cpp): contact trim, длина < 5 → ошибка формы; cell длина > 30 → ошибка формы; ошибки показываются на форме красным, редирект на форму не теряет введённое (flash/ModelMapper по вкусу coder'а). Определение телефон/артикул — `looksLikePhone` (порт `si/db.cpp:9-19`), вызвать в `DatabaseImpl.addOrder` (как задумано в лабе); пустой/несоответствующий контакт до БД не доходит из-за валидации формы.
- `application.yaml`: `spring.datasource.url: ${PICKUP_DB_URL:jdbc:postgresql://localhost:5432/pickup}`, `username: ${PICKUP_DB_USER:pickup_user}`, `password: ${PICKUP_DB_PASSWORD:pickup_pass}`; Flyway включён (по умолчанию), `spring.flyway.locations: classpath:db/migration`. DataSource/HikariCP уже на classpath через `spring-boot-starter-data-jdbc` (добавлен пользователем).
- Тесты: интеграционные на `DatabaseImpl` с Testcontainers PostgreSQL (создать контейнер, применить миграцию Flyway программно или `Jdbi` по контейнерному URL); контроллер — `@WebMvcTest`-стиль с моком `Database` (Spring Boot 4: `@MockitoBean`); валидация — параметризованные тесты.

## Чек-лист приёмки лабы (адаптация 18 пунктов к вебу — финальная ручная проверка человеком)

1. Сборка `gradlew.bat clean build` без ошибок/предупреждений (авто: t6).
2. Запуск без env — дефолты из application.yaml (веб-аналог подсказки PICKUP_DB не требуется; env override работает — t1).

4. Приёмка по телефону с ячейкой: `+79990001122`, `A1` → строка `PVZ-000001`, статус «К выдаче» (t5).
5. Приёмка по артикулу без ячейки: `ART-123456789` → `PVZ-000002`, ячейка «—» (t5).
6. Второй заказ на тот же телефон, ячейка `B12` → `PVZ-000003` (t5).
7. Короткий ввод `abc` → «Введите телефон или артикул посылки», заказ не создан (t5).
8. Поиск `+7999` → `PVZ-000001`, `PVZ-000003` (t5).
9. Поиск `ART-` → `PVZ-000002` (t5).
10. Поиск `000002` → `PVZ-000002` (t5).
11. Фильтр статуса: «К выдаче» — 3, «Выдан»/«Отменён» — пусто, «Все» — 3 (t4/t5).
12. Выдача `PVZ-000001` (confirm показывает телефон и ячейку A1) → зелёная строка, «Выдан» (t5).
13. Повторная выдача `PVZ-000001` → сообщение «Заказ нельзя выдать (статус: Выдан)», БД не меняется (t5).
14. Отмена `PVZ-000002` → красная строка, «Отменён» (t5).
15. Отмена выданного → «Отменить можно только заказ «К выдаче»», БД не меняется (t5).

17. Очистка истории: диалог «2» → согласие → остался `PVZ-000003` «К выдаче», статус-бар «Удалено заказов: 2» (t5).
